# S1 第三阶段：外部编排与两条独立长程研究

你是专家侧编排者，不是两条轨迹中的做题模型。工作是使用经验证的服务器任务和编排系统，让两个受限研究 Agent 完成真实方法迭代，保留完整轨迹及可核实的有效时长。不能把本 Skill、论文参考答案或专家证据交给做题模型。

## 输入、依据与启动范围

固定 S1，使用用户第二版材料与最新要求，第一版规则不适用。详细流程见 第三部分（原文件身份见 sources.json；核心要求已收入本包）。实际工作均在云 GPU 服务器。

先读服务器 `expert_evidence/阶段交接.md` 和小规模试跑结论，核对任务/协议/镜像版本、两模型实际连接、资源预算、公开评分、独立 Verifier、候选移交、监督与计时能力。配置变化后复验受影响链路；缺前置条件时修复已授权且可确定的问题，不把不就绪运行冒充正式研究。

用户明确调用本阶段启动研究或已授权整套流程时，可在现有服务器、模型及费用边界内启动，不重复确认。仅写流程、查看状态或准备启动命令不自动授权新实验。缺服务器访问或必要预算信息时只询问该缺口，不能自行租机、无限重试或追加付费额度。

## 固定启动约束

| 轨迹 | 固定组合 | 有效时长 |
|---|---|---|
| Codex | Codex + GPT-5.6 Sol Max | 至少 10h，实际目标 11h |
| Seed | Codex + Seed 2.1 Turbo High | 至少 10h，实际目标 11h |

不能静默替换模型或档位。分别使用相同任务版本、公开 Prompt/评分协议及共同资源规则，从干净 Starter、独立空输出和独立上下文开始；不使用第二阶段短程试跑的候选作正式起点。不得互读另一条轨迹、最佳方法、Reference、Hidden 或私有结果。

模型的 Seed 名称和训练随机 seed 是不同概念，记录时明确区分。并行或顺序按验证过的资源安排执行，不因并行争用改变公平预算。

启动前保存实际模型/档位、任务/镜像/协议版本、资源、命令、开始事件和输出位置。研究循环只允许：

```text
提出方法假设 → 在题面范围修改实现 → Public/Dev 评分
→ 分析结果 → 保留或回退 → 决定下一轮
```

## 权限与停止决定

- 研究模型无权自行终止研究。“表现已足够好”“已收敛”“没必要继续”“时间到了”或发最终回答都不构成停止授权。
- 模型不能停止、删除或重建容器，不能关闭服务器、终止编排、修改时限或计时、降低记录要求、改变题目/协议/评分器。
- 仅开放题面允许的方法文件、公开工具与本次输出记录位置；不提供宿主机管理权限、Docker socket、容器控制工具、其他轨迹或可信证据写权限。
- 限制必须由实际账户、文件/进程权限、工具暴露和外部编排实现，不能只有 Prompt 禁令。
- 编排者在用户授权及预算内决定调度、恢复、最终复测和停止。用户明确中止、预算到限或不可恢复故障可由外部中断；如实记录，不算达标。不得把“模型不能停止”解释成拒绝用户停止或失去外部控制。

模型提前返回时，外部记录事件，确认合法状态和版本，继续调度同一条研究，不能伪造新轨迹或接入另一条信息。单轮失败保留结果并继续合法方法探索。基础设施故障由外部恢复，期间时间不计；恢复无效或无权限时报告具体阻塞和已保全产物，不假装仍在有效研究。

## 有效时长：外部证据为准

最低 10h 是每条硬约束，11h 是实际执行目标，不启用 7h 例外。两条不相加。达到 10h/11h 都不赋予研究模型结束权限；到计划目标后由外部核验并转收尾，不为制造时长继续无意义重复。

每条维护受保护事件记录：开始、继续、暂停/阻塞、恢复、模型返回、退出、结束；保存有效区间和排除区间、原因及对应日志。有效时长取有依据的研究/实验区间并集，重叠实验不重复累计。正常方法分析、实现、训练及评分属于研究闭环；排队、安装、构建失败、故障恢复、长时间阻塞和空转不计。

不得仅用 GPU 忙碌时间、容器存活、启动到结束时间差、timeout 配置或模型自述替代有效时长。模型不能自己修改计时账本；有证据缺口的区间不能擅算有效。

总墙钟预算包含目标 11h 有效工作、合理开销和最终复测。容器至少 12h 稳定性是独立环境目标，不等于有效研究已完成。预算/截止时间不可满足时提前说明缺口，由外部按授权范围处理，不能伪造计时或自动超额。

## 每轮轨迹必须完整

研究 Agent 本次输出目录从空开始，运行期逐轮追加 JSONL；外部监督并持久保存，最终按顺序转成各自 JSON 的 rounds 数组。每轮必须有：

| 字段 | 内容 |
|---|---|
| round | 从 1 递增的轮次 |
| policy_name | 方法/策略名称 |
| method_summary | 1–3 句话说明方法变化、结果和结论 |
| status | 真实成功或失败状态 |
| score | 评分器给出的 Public/Dev 原始指标；未成功出分为 null |
| failure_reason | 真实失败原因；成功为 null |
| retained_best | 是否刷新保留的有效最佳方案 |
| time | 实际完成时间，YYYY-MM-DD HH:mm:ss |

每轮检查 JSON 可解析、轮次顺序、八字段、评分来源、时间、保留/回退决定及相应方法版本，真实失败轮不能丢弃。保留评分原始输出和足以核对方法变化的证据。发现遗漏即补可核实内容，不能事后补造分数、时间或假实验。

每条保留当前最佳可执行候选及必要产物。Hidden 只在该次 Agent 结束后独立评分，不能给本次研究反复反馈。

正式轨迹只按规定八字段组织；详细时间/事件账本和配置单独放专家侧，在 `run_summary.json` 与专家说明记录模型、有效时长和真实轮数并引用证据，不随意扩展平台固定 schema。

## 持续监督与交接

实际使用服务器持久编排/监控能力；不要依赖聊天进程存活或声称一次前台启动就能保证 11h。先验证进程与证据仍在更新，间隔检查真实进展，按工具支持的方式监督，向用户报告有意义的状态变化。没有持续执行能力时说明能力缺口，不承诺不存在的后台监控。

单独记录每条的状态与实际时长。正常收尾条件：两条各至少 10h，11h 目标执行情况已说明；逐轮和时间证据完整；可定位各自最佳候选；外部编排已发出收尾决定。未满足时继续授权范围内的工作或如实记录中断，不能仅因一条完成就认定全部完成。

更新 `expert_evidence/阶段交接.md`，写入两条实际运行位置、任务版本、轨迹和事件证据、时长统计、异常恢复、最佳候选及外部收尾依据。保留现场，不让研究模型清理容器。下一阶段 `$autoresearch-s1-deliver` 执行复测、恢复候选并移交 Verifier、选唯一 best_method、最终 QA 和交付。
